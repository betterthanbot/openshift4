# `argocd/` — What Bootstrap Hands Over To

`bootstrap/bootstrap.yaml` creates exactly one Application, pointed at this directory.
Everything ArgoCD manages afterwards is declared here, so this is the one folder where
adding a file changes what the cluster runs.

New to ArgoCD itself? Start with [docs/architecture.md](../docs/architecture.md) and
[docs/getting-started.md](../docs/getting-started.md) — this file covers only how *this*
repo is wired.

```
argocd/
  appProject.yaml         AppProject: openshift4-community — the trust boundary
  rbac-operands.yaml      ClusterRole/Binding letting ArgoCD create operator CRs
  appset-operators.yaml   ApplicationSet → one Application per operators/overlay/my-sno-cluster/*
  appset-workloads.yaml   ApplicationSet → one Application per overlay/my-sno-cluster/*
```

## The two ApplicationSets

**`appset-operators.yaml`** uses a *git directory* generator over
`operators/overlay/my-sno-cluster/*`. Every subdirectory becomes an Application named
`operators-<directory>` — a Kustomize overlay over `operators/bases/<directory>`, which
bundles one operator's OLM install with its operands. Adding an operator needs no edit to
this file; disabling one is an `exclude: true` entry, exactly like the workloads below
(`cert-manager`, `devworkspace`, `gitops`, `kmm-hub`, `lightspeed`, `quay` and
`workshop-auth` are excluded today). See [operators/README.md](../operators/README.md) for the
app list, how a sync is ordered and how to move a cluster over from the old
`operators-layer1` / `operators-layer2` pair.

**`appset-workloads.yaml`** uses a *git directory* generator over
`overlay/my-sno-cluster/*`. Every subdirectory containing a
`kustomization.yaml` becomes its own Application named after the directory — so adding a
workload needs no edit to this file at all:

```bash
mkdir overlay/my-sno-cluster/<name>   # + kustomization.yaml, push
```

To take a workload out of rotation without deleting it, add an exclusion instead:

```yaml
directories:
  - path: overlay/my-sno-cluster/*
  - path: overlay/my-sno-cluster/<name>
    exclude: true
```

`kyverno` and `get-a-username` are currently excluded this way.

## Things that will surprise you

**Nothing syncs itself.** `syncPolicy.automated` is commented out in both
ApplicationSets. Applications go `OutOfSync` on every repo change and stay there until
someone syncs — deliberate on this branch, but it means `OutOfSync` carries no signal
about health.

**The revision is `argocd/demo`, in three places.** `bootstrap/bootstrap.yaml` and both
ApplicationSets each pin `repoURL` and `targetRevision` independently. Forking means
changing all three.

**`ignoreDifferences` protects runtime-mutated objects.** In `appset-workloads.yaml`,
`gatus-config` is generated by a discovery CronJob at runtime, and `get-a-username-secret`
holds a real password set by hand on the cluster. `appset-operators.yaml` carries a longer
list — placeholder Secrets whose real credentials are entered by hand, the Grafana bearer
token, operator-owned status. The list is shared by every generated app, so an entry that
matches nothing in a given app is a no-op there. Add an entry for any object the cluster is
expected to own more authoritatively than git does.

**The two ApplicationSets differ on deletion.** `appset-operators.yaml` sets
`preserveResourcesOnDeletion: true`; `appset-workloads.yaml` leaves the default (`false`).
With the default, every generated Application carries a cascade-delete finalizer, so
removing the Application (or its `exclude` entry) deletes what it deployed. That is fine for
Gatus; it is not for LokiStack or the DataScienceCluster, so operator apps only *stop being
managed* when removed. See the comment in `appset-operators.yaml` before changing it.

**No ordering between Applications.** Sync waves order the resources inside one
Application, not separate Applications generated by an ApplicationSet. An app that needs
another app's CRDs retries until they exist (`retry.limit: 10`). `SkipDryRunOnMissingResource`
is what lets that happen without the whole sync being rejected.

**`orphanedResources.warn: true`** in `appProject.yaml` is why every workload Application
shows `OrphanedResourceWarning: 134 orphaned resources`. Those namespaces contain plenty
ArgoCD did not create. It is noise, not a fault — turn the flag off if it stops being
useful.

**The AppProject is deliberately wide open** — `clusterResourceWhitelist` and
`namespaceResourceWhitelist` are both `*`/`*`, and destinations allow every namespace.
The file says to tighten this once the cluster is stable; that has not happened yet.

## `rbac-operands.yaml`

ArgoCD's controller does not get permission to create arbitrary operator CRs by default.
This grants it the API groups the operator bundles use — Grafana, NVIDIA ClusterPolicy,
DataScienceCluster/DSCInitialization, RHACS Central/SecuredCluster, Compliance scan
settings, ClusterLogForwarder, LokiStack, NodeFeatureDiscovery, plus the core
ServiceAccount/Secret/RBAC/Job verbs those bases use.

The same file also binds the controller to `cluster-admin` (the last document), so the
narrower ClusterRole is belt-and-braces: a new operand kind in `operators/bases/` will not
by itself fail with a forbidden error, but listing its group here keeps the file honest if
that binding is ever removed.
