# Tech Debt / Known Issues

Findings from a MaaS + observability troubleshooting session on 2026-07-23/24, cluster
`cluster.example.com`. Kept here so fixes/workarounds and their
root causes aren't lost. Several of these are upstream/product bugs (RHOAI operator,
RHCL/Kuadrant, Service Mesh) rather than something wrong in this repo.

## 1. Grafana dashboards missing datasource mapping (fixed in repo)

**Symptom:** All Grafana MaaS dashboards showed `No datasource found for kind
'PrometheusDatasource' and name 'undefined'`.

**Root cause:** [bases/grafana/generate_dashboards.sh](bases/grafana/generate_dashboards.sh)
never set `spec.datasources` on the generated `GrafanaDashboard` CRs, so the
`${DS_PROMETHEUS}` template variable in every dashboard JSON (a placeholder created by
Grafana's "export for sharing externally") was never resolved to a real datasource UID by
the grafana-operator.

**Fix:** Added the missing mapping to the generator template:
```yaml
spec:
  datasources:
    - inputName: "DS_PROMETHEUS"
      datasourceName: "Prometheus"
```
All 15 dashboards under [bases/grafana/generated/](bases/grafana/generated/) were
regenerated. This affected every dashboard the script produces, not just the MaaS ones.
**Status:** fixed in git; needs to sync out via GitOps/ArgoCD to take effect on cluster.

## 2. Native RHOAI "Observe & monitor" dashboard — no default Prometheus datasource (operator bug, worked around manually)

**Symptom:** The RHOAI console's own Observability dashboard (Cluster/Models tabs, Perses-based,
not Grafana) showed the same `PrometheusDatasource`/`undefined` error, but with no config in
this repo to fix — these `PersesDashboard`/`PersesDatasource` resources are auto-generated by
the `rhods-operator`.

**Root cause:** the `rhods-operator`'s `Monitoring` service controller fails to reconcile
because a separate, unrelated manifest it generates (`redhat-ods-monitoring/tempo-datasource`,
a `PersesDatasource` for Tempo traces) is invalid — its `spec.client.tls.caCert` is missing the
required `namespace` field:
```
PersesDatasource.perses.dev "tempo-datasource" is invalid: spec.client.tls.caCert:
Invalid value: "object": namespace is required when type is secret or configmap
```
This failure aborts the whole batch apply for that reconcile pass, so the Prometheus
`PersesDatasource` that the Cluster/Models dashboards need (no explicit `name`, relies on a
`default: true` datasource) never gets created. Retries continuously (~1/sec), spamming logs.

**Workaround applied (manual, not GitOps-tracked):** created
`PersesDatasource/prometheus-datasource` in `redhat-ods-monitoring`, `default: true`, pointing
at `thanos-querier-data-science-thanos-querier.redhat-ods-monitoring.svc:10902`.

**Caveat:** this is a stopgap. It isn't tracked in git or owned by the operator — an operator
upgrade/reinstall could wipe or duplicate it. The underlying Tempo-datasource manifest bug
should be filed against `opendatahub-operator`.

## 3. Missing NetworkPolicy rule blocks the data-science Thanos Querier from its own Prometheus (worked around manually)

**Symptom:** After fixing #2, dashboard panels stopped showing the datasource error but showed
"No data" instead.

**Root cause:** `NetworkPolicy/data-science-prometheus-instance-ingress` in
`redhat-ods-monitoring` (also auto-generated by the `rhods-operator` Monitoring controller)
only allows ingress to the Prometheus pod on port 9090 from two specific proxy pods. It never
opens port **10901** (the Thanos gRPC sidecar port), so
`thanos-querier-data-science-thanos-querier` could resolve the sidecar via DNS but every gRPC
connection attempt silently timed out (`context deadline exceeded while waiting for
connections to become ready`), leaving `/api/v1/stores` empty and every query empty.

**Workaround applied:** added a supplementary, additive `NetworkPolicy`
(`thanos-querier-data-science-to-prometheus-sidecar`) opening port 10901 from pods labeled
`app.kubernetes.io/instance=thanos-querier-data-science-thanos-querier`. NetworkPolicies are
OR'd together, so this doesn't touch or conflict with the operator-owned one.

**Caveat:** same as #2 — not GitOps-tracked, should be filed upstream.

## 4. Data-science Prometheus (`monitoring.rhobs/v1`) can't see cross-namespace metrics — deliberate isolation, not a bug (worked around manually, 2026-07-24)

**Symptom:** After #2 and #3, GPU/self-monitoring metrics flow, but the dashboard's other
panels (System health, Deployed models, Request success rate, Cluster resource overview) still
show no data.

**Root cause, layered:**
- This Prometheus uses the `monitoring.rhobs/v1` CRD group (cluster-observability-operator),
  not the standard `monitoring.coreos.com/v1` group everything else on the cluster uses — so it
  doesn't see any of the existing `ServiceMonitor`/`PodMonitor` objects (kube-state-metrics,
  node-exporter, the vLLM engine `PodMonitor`s in `vllm-project`) even though its own selectors
  are empty (`{}` = match all).
- Its `podMonitorNamespaceSelector`/`serviceMonitorNamespaceSelector` are unset, so even a
  `monitoring.rhobs/v1` `PodMonitor`/`ServiceMonitor` is only discovered if the **object itself**
  lives in `redhat-ods-monitoring`.
- More fundamentally: verified via the generated scrape config that Kubernetes service
  discovery is **hardcoded to `namespaces: names: [redhat-ods-monitoring]`**, regardless of the
  `PodMonitor`'s own `namespaceSelector: {}`. Tested this directly — created a `monitoring.rhobs/v1`
  `PodMonitor` in `redhat-ods-monitoring` targeting vLLM pods in `vllm-project`; it was correctly
  loaded into the Prometheus config but discovered zero targets, because discovery never leaves
  the Prometheus's own namespace. This looks like intentional per-tenant isolation for this
  "MonitoringStack" pattern, not an oversight — reverted the test `PodMonitor`.
- **Correction (2026-07-24):** the original write-up said `accelerator_gpu_utilization` and
  `kserve_vllm:*` "don't exist anywhere on the cluster as `PrometheusRule` objects" — that was
  only checked against the isolated data-science Thanos. They DO exist on the cluster's global
  Thanos Querier (`openshift-monitoring`): `accelerator_gpu_utilization` is a recording rule
  shipped by the NVIDIA GPU Operator itself (`PrometheusRule/nvidia-dcgm-exporter` in
  `nvidia-gpu-operator`, owned by `ClusterPolicy/gpu-cluster-policy`), and `kserve_vllm:*` are
  literal metric names emitted directly by the vLLM engine (not a recording rule at all). Both
  namespaces (`nvidia-gpu-operator`, `vllm-project`) carry `openshift.io/cluster-monitoring:
  "true"`, so the global `openshift-monitoring/k8s` Prometheus scrapes them directly alongside
  standard kube-state-metrics/node-exporter/cAdvisor. Confirmed live: every panel query in both
  `dashboard-0-cluster-admin` and `dashboard-1-model` returns real data against the global Thanos
  Querier (`thanos-querier.openshift-monitoring.svc:9091`).

**Workaround applied (manual, not GitOps-tracked):** repointed the shared default
`PersesDatasource/prometheus-datasource` (redhat-ods-monitoring) at the global Thanos Querier
instead of the isolated one. Since neither `dashboard-0-cluster-admin` nor `dashboard-1-model`
reference a datasource by name (both rely on `default: true`), this one change fixes both tabs.
Three new objects, all additive (nothing operator-owned was edited):
- `ConfigMap/thanos-querier-serving-ca` (redhat-ods-monitoring) — annotated
  `service.beta.openshift.io/inject-cabundle: "true"` so service-ca-operator populates the CA
  that signs `thanos-querier.openshift-monitoring.svc`'s serving cert.
- `ClusterRoleBinding/data-science-perses-cluster-monitoring-view` — binds the built-in
  `cluster-monitoring-view` ClusterRole to `system:serviceaccount:redhat-ods-monitoring:default`
  (the SA the Perses server pod runs as — it has no dedicated SA). Same pattern already used by
  `grafana-sa` and `rhods-dashboard` on this cluster. Caveat: `default` in this namespace is also
  used by the data-science Thanos Querier pod, so it picks up this read-only grant too (low risk).
- A Perses-native `Secret` (`prometheus-datasource-manual-secret`, created via the Perses HTTP
  API at `/api/v1/projects/redhat-ods-monitoring/secrets`, not a Kubernetes object) holding the
  CA plus a Bearer token for that same SA (`oc create token default -n redhat-ods-monitoring
  --duration=8760h`, ~1 year — will need manual renewal before expiry).

**Dead end worth recording:** `PersesDatasource.spec.client.tls`/`.kubernetesAuth` (the
"official" COO-CRD fields for datasource auth/TLS) looked like the right tool and partially
worked — `client.tls.caCert` (ConfigMap ref) does get wired into the datasource's outbound TLS
trust. But `client.kubernetesAuth.enable: true` never attached a bearer token to the actual proxy
call (still got 401s from Thanos's kube-rbac-proxy) despite the RBAC above being verified correct
with a manually-supplied token. Worse, the `perses-operator` resyncs **every PersesDatasource
object cluster-wide roughly every 30-60s**, unconditionally regenerating the datasource's
Perses-native secret from `spec.client.*` — so directly PATCHing the operator-managed secret via
the Perses API to add the missing `authorization` field gets silently wiped on the next resync.
Worked around by dropping `spec.client` from the CR entirely and pointing
`spec.config.plugin.spec.proxy.spec.secret` at a separately-named Perses secret the operator never
touches. If `kubernetesAuth` gets fixed upstream in a future COO release, this whole secret
dance can likely collapse back down to just `client.tls` + `client.kubernetesAuth: {enable: true}`
— worth retesting after an operator upgrade.

**Status:** working as of 2026-07-24. Not GitOps-tracked (same caveat as #2/#3) — an operator
upgrade/reinstall could revert the datasource CR to its broken default, and none of the three new
objects are declared anywhere in this repo.

## 5. `maas-default-gateway` pod OOMKilled — RHCL/Service Mesh version-skew bug (mitigated, not fixed)

**Symptom:** `maas-default-gateway-openshift-default-*` pod in `openshift-ingress` in constant
`CrashLoopBackOff`, `istio-proxy` container `OOMKilled` (exit 137) on a ~5 min cycle, taking the
whole `maas.apps.<cluster>` hostname down.

**Root cause:** the `kuadrant-maas-default-gateway` `EnvoyFilter` (auto-generated by the RHCL/Kuadrant
operator from the `AuthPolicy`/`RateLimitPolicy`/`TokenRateLimitPolicy` resources) injects a WASM
HTTP filter config containing `allow_on_headers_stop_iteration: true`. The `istio-proxy` Envoy
build doesn't recognize that field:
```
Unknown field: ... no such field: 'allow_on_headers_stop_iteration'
```
Each rejected WASM remote-fetch retry leaks memory until the container hits its limit. Traced to
a recent operator upgrade: `rhcl-operator` (Connectivity Link / Kuadrant) 1.3.5 → 1.4.1, and
`servicemeshoperator3` 3.1.0 → 3.4.0, happening at almost the same time the pod started
crash-looping — points to a version-skew bug between the two. The `EnvoyFilter` is
force-reconciled by the operator, so hand-editing it reverts immediately.

**Mitigation applied** (does not fix the leak, buys headroom + redundancy): created
`ConfigMap/maas-default-gateway-options` in `openshift-ingress` and patched
`Gateway/maas-default-gateway`'s `spec.infrastructure.parametersRef` to point at it (the
supported, non-reverted customization point for Gateway-API-managed deployments):
- istio-proxy memory: limit `1Gi → 3Gi`, request `128Mi → 256Mi`
- replicas: `1 → 2`
- `PodDisruptionBudget` with `minAvailable: 1`

**Status:** mitigated, not fixed. The WASM leak is still present; each replica will still
eventually OOM, just less often, and a second replica means one crashing doesn't take the
hostname down entirely. Real fix needs either an RHCL/Service-Mesh compatibility patch or
rolling `rhcl-operator` back to 1.3.5.

## 6. MaaS Usage Overview dashboard — no per-user volume metrics (known/documented limitation, not a bug)

Documented directly in the dashboard's own `description` field
([bases/grafana/dashboard/RHOAI MaaS Usage Overview.json](bases/grafana/dashboard/RHOAI%20MaaS%20Usage%20Overview.json)):
there is no per-user token/request volume anywhere on this cluster. Limitador and
`istio_requests_total` carry no user label (Kuadrant deliberately avoids per-user Prometheus
cardinality), and `maas-api`'s Postgres table only stores `last_used_at`, not a usage counter.
The "Users & API Keys" table is a live identity/access list (recency signal via
`last_used_at`), not a usage breakdown. True per-user volume needs the still-blocked
Loki/Istio-access-log path (see the "RHOAI MaaS User & API Key Drilldown" dashboard).

**Note (2026-07-24):** this "no user label" claim is worth re-checking — see #7. This same
cluster's Limitador CR has `telemetry: exhaustive` (`--limit-name-in-labels`) and its
`RateLimitPolicy`/`TokenRateLimitPolicy` limits are keyed on `auth.identity.userid`, which is
what the *native Perses* Usage tab's queries (`authorized_hits{user=...}` etc.) depend on. Whether
that's actually sufficient for Grafana's differently-shaped Usage Overview dashboard wasn't
re-verified — but the "Kuadrant deliberately avoids per-user cardinality" framing above may be
stale. Either way, #7 found the more fundamental problem: right now these metrics have zero
samples regardless of labels, because Limitador isn't recording the traffic at all.

## 7. Native "Observe & monitor" dashboard, Usage tab — datasource auth fixed, but Limitador emits zero rate-limit metrics (2026-07-24)

**Symptom:** Unlike the Cluster/Models tabs (#4), the Usage tab (`dashboard-3-maas-usage-admin`)
was previously believed to "just work" (see `perses-dashboard-maas-usage.yaml`'s original header).
It doesn't — every Overview stat (Total Tokens, Total Requests, Total Errors, Active Users) shows
`0`, Success Rate shows `100%`.

**Root cause, two independent layers:**

1. **`kuadrant-prometheus-datasource` was returning 401 Unauthorized**, same class of bug as #4:
   `spec.config.plugin.spec.proxy.spec.secret: kuadrant-prometheus-datasource-secret` referenced a
   Kubernetes Secret that never existed on this cluster. Every panel query against it failed
   silently — the dashboard doesn't surface an error banner for a failed datasource call, it just
   renders whatever the query's `or vector(0)` / `or vector(1)` fallback produces, which is
   indistinguishable from "genuinely zero usage" at a glance. **Fixed** the same way as #4:
   `RoleBinding/data-science-perses-view` (namespace-scoped `view` ClusterRole in `kuadrant-system`
   — port 9092's tenancy-scoped API needs `view` in the target project, not
   `cluster-monitoring-view`) plus a separately-named Perses-native secret
   (`kuadrant-prometheus-datasource-manual-secret`) carrying the CA (reused the existing
   `prometheus-web-tls-ca` ConfigMap in `redhat-ods-applications`, which was already correctly
   wired) and a bearer token for `redhat-ods-monitoring/default`. Confirmed working end-to-end —
   `up`, `limitador_up`, etc. now return real data through this datasource.

   Side note while testing: querying Perses' own `/proxy/...` endpoint for a datasource in a
   **different project** than `redhat-ods-monitoring` (where the Perses pod itself lives) enforces
   its own Kubernetes-native RBAC check on the caller — an unauthenticated request gets a
   confusingly-labeled `403 Forbidden (verb=create, resource=pods)` regardless of the actual
   query. This isn't a bug affecting real users (the RHOAI console forwards the logged-in user's
   own token), just a trap for anyone testing via `oc port-forward` + bare `curl` like this
   session did — pass a real bearer token (`Authorization: Bearer $(oc whoami -t)`) when testing
   directly.

2. **Even with the datasource fixed, `authorized_hits`/`authorized_calls`/`limited_calls` don't
   exist anywhere on the cluster** — confirmed both via the fixed datasource and by reading
   Limitador's `/metrics` endpoint directly (`oc exec deploy/limitador-limitador -n kuadrant-system
   -- curl localhost:8080/metrics`), which currently exposes only `limitador_up` and
   `datastore_partitioned`. This is *not* the same gap as #6 (Grafana's "MaaS Usage Overview"
   description claims Limitador "carries no user label" at all) — this Limitador instance has
   `telemetry: exhaustive` and `--limit-name-in-labels` set, and `RateLimitPolicy`/
   `TokenRateLimitPolicy` objects with real configured limits (`team-alpha-tier-requests`,
   `team-bravo-tier-requests`, etc.) exist and are active. Real HTTP traffic is also demonstrably
   flowing — `istio_requests_total` shows ~580 requests/6h to `vllm-project` — yet Limitador's own
   counters never increment. That combination (configured limits + real traffic + zero counters)
   points at the traffic never actually reaching Limitador's rate-limit-check path at all, i.e.
   the `istio_requests_total` traffic seen may not be going through the Kuadrant-protected gateway
   route/WASM filter chain (possibly related to the WASM filter instability in #5) — **not
   investigated further this session**, this needs its own trace-level dig (Envoy access logs on
   the gateway pod, or Kuadrant's own request-level tracing) to confirm.

**Status:** datasource auth fixed and committed
(`dumps/maas-extract/observability/perses-datasources.yaml`,
`dumps/maas-extract/observability/perses-thanos-rbac.yaml`). The zero-metrics finding is not
fixed — it's a genuine "Limitador isn't seeing this traffic" gap, separate from anything
dashboard-related, and needs someone to trace an actual request through the gateway to find where
it diverges from the Kuadrant enforcement path.
