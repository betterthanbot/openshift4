# Operator Management

This guide explains how to enable, disable, add and upgrade the operators managed by this repo. All changes are made in YAML files and applied via GitOps — no manual OperatorHub clicks required.

For the layout, the full list of apps and how syncing behaves, see `operators/README.md` in the repo. This page is the task-oriented version.

---

## How operators are managed

Every operator is its own **base**, **overlay** and **ArgoCD app**:

| Piece | Path | What it is |
|-------|------|------------|
| Base | `operators/bases/<name>/` | The operator's OLM install (`namespace.yaml`, `operatorgroup.yaml`, `subscription.yaml`) *and* the custom resources that configure it |
| Overlay | `operators/overlay/my-sno-cluster/<name>/` | What this cluster changes (usually nothing, sometimes a patch) — the ArgoCD app points here |
| App | `operators-<name>` | Generated by `argocd/appset-operators.yaml`; one per overlay directory |

The install and the operands are in one app, so a single sync installs the operator and then
configures it: sync waves run `Namespace` (-3) → `OperatorGroup` (-2) → `Subscription` (-1) → operands (0+),
and ArgoCD waits for the Subscription to report healthy before the operands are applied.

Today 17 of the 23 declared operators are enabled. Disabled: OpenShift GitOps (the cluster provides it), KMM Hub, cert-manager (the sandbox ships it), Lightspeed, Quay and DevWorkspace.

## Disabling an operator

Disabled operators keep their base and overlay in git; they just get no ArgoCD Application. Add an `exclude` entry to `argocd/appset-operators.yaml`:

```yaml
directories:
  - path: operators/overlay/my-sno-cluster/*
  - path: operators/overlay/my-sno-cluster/rhacs
    exclude: true
```

Commit, push, then sync the `bootstrap` Application so the ApplicationSet is regenerated.

> **This does not uninstall anything.** The ApplicationSet sets `preserveResourcesOnDeletion: true`, so
> when the `operators-rhacs` Application disappears, the Subscription, Central, SecuredCluster and the
> `stackrox` namespace are left running. That is deliberate — it protects LokiStack, the DataScienceCluster
> and their volumes from an accidental delete.

To actually uninstall, delete the app *with cascade* **before** excluding it:

```bash
argocd app delete operators-rhacs --cascade        # removes the Subscription, operands and Namespace
```

then add the `exclude` entry, and clean up what OLM leaves behind (deleting a Subscription does not delete its CSV):

```bash
oc get csv -n stackrox
oc delete csv -n stackrox <csv-name>
```

## Enabling an operator

Remove its `exclude: true` entry from `argocd/appset-operators.yaml`, push, and sync `bootstrap`. The new
`operators-<name>` Application appears; sync it. Check the header of
`operators/bases/<name>/kustomization.yaml` for anything it needs first (for example `gpu-operator` wants
`nfd`, `maas` wants `rhoai`).

If the operator is already installed on the cluster (such as GitOps or cert-manager on a sandbox), check
that its base matches what is installed before you sync — the app will adopt the existing objects.

## Adding a new operator

### Step 1 — Create the base

```bash
mkdir operators/bases/my-operator
```

`namespace.yaml`:

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: my-operator-namespace
  labels:
    kubernetes.io/metadata.name: my-operator-namespace
  annotations:
    argocd.argoproj.io/sync-wave: "-3"
```

`operatorgroup.yaml`:

```yaml
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: my-operator
  namespace: my-operator-namespace
  annotations:
    argocd.argoproj.io/sync-wave: "-2"
spec: {}    # AllNamespaces. Use `targetNamespaces: [my-operator-namespace]` for OwnNamespace.
```

`subscription.yaml`:

```yaml
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: my-operator-package-name      # OLM package name from OperatorHub
  namespace: my-operator-namespace
  annotations:
    argocd.argoproj.io/sync-wave: "-1"
spec:
  channel: stable
  name: my-operator-package-name
  source: redhat-operators            # or community-operators, certified-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Automatic
  startingCSV: my-operator.v1.2.3     # optional; omit to track the head of the channel
```

To find the right `name`, `channel` and `source`, browse OperatorHub in the OpenShift Web Console or run:

```bash
oc get packagemanifests -n openshift-marketplace | grep <operator-name>
oc get packagemanifest <name> -n openshift-marketplace -o yaml | grep -E "channel|defaultChannel"
```

An operator that installs into `openshift-operators` (which already has the `global-operators` OperatorGroup) needs
only the Subscription — see `operators/bases/service-mesh`.

### Step 2 — Add its operands (optional)

If the operator needs custom resources to do anything, add them as files in the same directory. **Every operand
CR needs this annotation**, or a cold-bootstrap sync is rejected before anything is applied (see
`techdebt.md` item 14):

```yaml
metadata:
  annotations:
    argocd.argoproj.io/sync-options: SkipDryRunOnMissingResource=true
```

Leave `sync-wave` unset unless the operands must be ordered among themselves; they run after the
Subscription either way.

### Step 3 — Write the kustomization and the overlay

`operators/bases/my-operator/kustomization.yaml`:

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

resources:
  - namespace.yaml
  - operatorgroup.yaml
  - subscription.yaml
  - my-operand.yaml
```

`operators/overlay/my-sno-cluster/my-operator/kustomization.yaml`:

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization

resources:
  - ../../../bases/my-operator
```

### Step 4 — Check it builds, commit and push

```bash
kustomize build operators/overlay/my-sno-cluster/my-operator
```

The ApplicationSet discovers the new overlay directory and creates `operators-my-operator`; no ArgoCD file needs
editing. ArgoCD already has `cluster-admin` (`argocd/rbac-operands.yaml`), so no extra RBAC is needed.

## Pinning an operator to a specific version

`startingCSV` alone is only a floor: with `Automatic` approval OLM installs it and then upgrades to the head of the
channel. To hold a version, set `installPlanApproval: Manual` as well, in `operators/bases/<name>/subscription.yaml`:

```yaml
spec:
  installPlanApproval: Manual
  startingCSV: my-operator.v1.2.3
```

With `Manual` approval, OLM creates an `InstallPlan` but waits for a human before upgrading. Approve via CLI:

```bash
oc get installplan -n <namespace>
oc patch installplan <name> -n <namespace> \
  --type merge -p '{"spec":{"approved":true}}'
```

> A `Manual` Subscription that has never been approved also holds back *its own app's* operands — ArgoCD waits for
> the Subscription to be healthy before applying them. Approve the first InstallPlan to let the sync continue.

## Changing an operator channel

To track a different release channel, update `channel` in `operators/bases/<name>/subscription.yaml`:

```yaml
spec:
  channel: stable-6.3   # was stable-6.2
```

Commit and push — OLM will upgrade the operator to the latest CSV in the new channel on the next reconcile. Keep the
tables in `VERSIONS.md` in step.

## Compliance Operator — managing scan profiles

Compliance scans are configured in `operators/bases/compliance/` — `scansettings.yaml` for schedules and storage,
`scansettingbindings.yaml` for which profiles run. To add a profile binding, append a document to
`scansettingbindings.yaml`:

```yaml
---
apiVersion: compliance.openshift.io/v1alpha1
kind: ScanSettingBinding
metadata:
  name: my-scan
  namespace: openshift-compliance
  annotations:
    argocd.argoproj.io/sync-options: SkipDryRunOnMissingResource=true
profiles:
  - apiGroup: compliance.openshift.io/v1alpha1
    kind: Profile
    name: ocp4-cis-1-7
settingsRef:
  apiGroup: compliance.openshift.io/v1alpha1
  kind: ScanSetting
  name: cis-1.7-full    # reference an existing ScanSetting
```

List available profiles:
```bash
oc get profiles.compliance -n openshift-compliance
```
